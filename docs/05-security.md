# Безопасность сайта, приложения и CRM

Это набор **[Рекомендаций]**. Проверяемые основания: авторизация [S14], SQL [S15], SSRF [S16], ресурсные ограничения [S11]. Не статистический рейтинг распространённости.

## Самая важная граница — backend

Мобильный клиент и браузер считаются недоверенными. Скрытая кнопка, CORS, UUID и обфускация JS не заменяют права доступа. На каждой операции проверяйте субъект, tenant, объект, действие и разрешённые поля. Для обновления профиля нельзя без фильтра копировать все поля JSON в модель: роль и tenant определяет сервер.

Для CRM нужен тест: пользователь организации A не может читать, менять, экспортировать или скачать вложение организации B, даже зная идентификатор. Проверьте также поиск, массовые операции, фоновые задачи и ссылки на файлы. Очередь должна нести проверенный контекст, а права на получение результата проверяются заново.

## Уязвимости и контроль

| Класс | Ошибка | Защита и конкретная проверка |
|---|---|---|
| SQL injection | Склейка пользовательской строки и SQL | Параметризованные значения; allowlist сортировок/полей; проверить raw SQL внутри ORM [S15] |
| SSRF | Сервер скачивает произвольный URL клиента | Разрешённые назначения, контроль redirect/DNS, запрет внутренних сетей, ограниченный egress [S16] |
| XSS | Недоверенный HTML вставляется как готовая разметка | Контекстное экранирование, санитайзер при необходимости HTML; CSP как дополнительный слой |
| CSRF | Cookie-сессия допускает стороннюю команду | CSRF-защита фреймворка, проверка origin где применимо, корректные cookie-параметры |
| Секреты | Ключ в frontend, git или логах | Backend-хранение, минимальные права, исключение из логов; при утечке ротация, а не только удаление файла |
| Загрузка файлов | Доверие расширению и имени | Проверка типа/размера, карантин, случайное имя, запрет исполнения, отдельная выдача |
| Webhooks | Доверие факту POST | Подпись по контракту провайдера, проверка времени, дедупликация event_id |
| Гонки | Проверка остатка отдельно от списания | Транзакции/условная запись и ограничения БД; тест конкурентных операций |
| Утечки кэша | Общий ключ для приватного результата | Ключи с tenant/контекстом доступа, проверка политик кеширования |

Для XSS/CSRF/секретов/webhooks здесь дан проектный чек-лист; конкретные параметры следует брать из документации выбранного фреймворка и провайдера, которой в этом исследовании нет.

## Инфраструктура и процесс

БД не должна быть общедоступным сервисом только потому, что у неё есть пароль. Разделите учётки приложения, миграций и администрирования. Включите MFA для административных доступов, своевременное обновление зависимостей и учёт production-изменений. Не выдавайте CI полные права на облако для обычных тестов.

Логи нужны для расследования, но не должны содержать токены, пароли и полные клиентские выгрузки. Аудит изменений прав храните отдельно от обычного изменяемого объекта. Проверяйте, что старый сотрудник/токен действительно теряет доступ после отзыва.

Бэкап хранится отдельно от основной области отказа; восстановление включает ключи, конфигурацию и файлы. Реплика не заменяет backup: ошибочное удаление может распространиться на неё. Урок GitLab [S08] — проверять восстановление и процедуры, а не наличие расписания.

## Что проверить до открытия регистрации

Путь регистрации/логина/восстановления, доступ между организациями, создание и отзыв ключей, экспорт и удаление клиента, ограничения ресурсов и платных интеграций. Отдельно протестировать обычного пользователя с прямым HTTP-клиентом, без ограничений UI.
