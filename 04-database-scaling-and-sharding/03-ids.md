# Идентификаторы в распределённых системах: Snowflake, Instagram-ID, ULID, UUIDv7

> Уверенность: **H** (спецификации и первоисточники; Instagram — **M/partial**: первоисточник не открылся напрямую по таймауту, данные подтверждены через поисковый индекс страницы и её копии).

## Зачем думать об ID заранее
- Автоинкремент привязан к одной БД: при шардировании нужны глобально уникальные ID.
- Последовательные ID в URL позволяют перечислять объекты (Parler — [Wired](https://www.wired.com/story/parler-hack-data-public-posts-images-video/)) — это не уязвимость сама по себе, но усиливает IDOR и скрейпинг.
- Полностью случайные UUIDv4 фрагментируют B-tree индексы; ULID-спека прямо называет это минусом v4 ([ULID spec](https://github.com/ulid/spec)).

## Варианты

| Схема | Состав | Плюсы | Минусы |
|---|---|---|---|
| **Instagram** (2012) | 64 бита: 41 бит — миллисекунды от своей эпохи, 13 бит — логический шард, 10 бит — последовательность mod 1024 (до 1024 ID на шард в мс); генерация функцией PL/pgSQL в самой Postgres ([Instagram](https://instagram-engineering.com/sharding-ids-at-instagram-1cf5a71e5a5c)) | bigint, сортируемы по времени, шард «зашит» в ID | Шард в ID мешает переносить данные между логическими шардами без смены ID |
| **Twitter Snowflake** | Сервис генерации 64-битных ID; исходный релиз выведен из эксплуатации ([twitter-archive/snowflake](https://github.com/twitter-archive/snowflake)) | Время-сортируемы | Отдельный сервис, зависимость от часов |
| **Discord Snowflake** | 64 бита, старшие 42 бита — мс от эпохи Discord (2015); в HTTP API отдаются **строками**, чтобы избежать переполнения целых в некоторых языках ([Discord API Reference](https://discord.com/developers/docs/reference)) | Используются как clustering key для сообщений ([Discord](https://discord.com/blog/how-discord-stores-billions-of-messages)) | — |
| **Sonyflake** | Вариант Snowflake ([sonyflake](https://github.com/sony/sonyflake)) | | |
| **ULID** | 128 бит: время + 80 бит случайности; Crockford base32; лексикографически сортируем; монотонность в пределах мс ([ULID spec](https://github.com/ulid/spec)) | Без координации, сортируемы, совместимы с UUID-колонкой | 128 бит; время создания раскрывается |
| **UUIDv7** (RFC 9562) | Поле `unix_ts_ms` + случайность; time-ordered ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)) | Стандарт, нативный тип `uuid` в Postgres | Раскрывает время создания |
| **KSUID** | Время + случайность ([segmentio/ksuid](https://github.com/segmentio/ksuid)) | | |

## Важно для TypeScript
- `Number` в JS безопасен только до 2^53 − 1; 64-битные ID отдавайте в API **строками** (как Discord) и храните как `bigint`/строку в коде. Иначе последние цифры ID молча искажаются.

## Рекомендация для соло-проекта (**M**)
- По умолчанию: **UUIDv7** как первичный ключ (тип `uuid`), генерация в приложении или БД. Сортируемость по времени даёт локальность индексов, а отсутствие координации — свободу будущего шардирования.
- Если нужен компактный `bigint` — Snowflake-подобная схема с *логическим* шардом/воркером, но помните ловушку Figma: время-префиксные ID дают hot spots при range-шардировании → маршрутизируйте по hash ([Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)).
- Публичные ID ≠ гарантия безопасности: авторизация всё равно обязательна.
- Пример генерации UUIDv7 — `examples/db/ids.ts`.

## Что делать / чего не делать

**Делать**
- Выбрать глобально уникальные, time-ordered ID (UUIDv7/ULID) с первого дня.
- Отдавать 64-битные числовые ID строками в JSON.
- Проверять права на объект независимо от «угадываемости» ID.

**Не делать**
- Не использовать автоинкремент как публичный ID в URL для приватных объектов.
- Не использовать UUIDv4 как кластерный/первичный ключ огромных таблиц без понимания цены для индексов.
- Не range-шардировать по монотонному ID.
