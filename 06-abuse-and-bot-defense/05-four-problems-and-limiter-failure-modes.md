# Бот соблюдает лимит и меняет аккаунт: почему защита не работает

> Теги **[Факт]/[Рекомендация]/[Пример]/[Ограничение]** и ссылки вида `[S01]` расшифрованы в [методике](../00-methodology.md) и [реестре первичных источников](../sources/primary-registry.md).

**[Факт]** OWASP отдельно рассматривает чрезмерное потребление ресурсов (API4) и автоматизацию чувствительных бизнес-процессов (API6) [S11, S12]. Cloudflare описывает ограничения количества и сложности GraphQL-операций [S13]. Ниже — **авторская модель защиты**, не готовая конфигурация этих продуктов.

## Разделите четыре проблемы

| Проблема | Что пытаются получить | Основной объект защиты |
|---|---|---|
| Подбор пароля | Чужой доступ | Аутентификация и восстановление учётки |
| Перегрузка API | Недоступность или дорогие вычисления | Пропускная способность и бюджет |
| Массовое создание учёток | Новые квоты/бонусы | Регистрация и выдача привилегий |
| Злоупотребление действием | Спам, резервирование, выгрузка | Конкретный бизнес-процесс |

Защищённый SSH не означает защищённый HTTP API. Успешная авторизация бота не делает его запросы экономически приемлемыми.

**[Пример]** При 60 запросах в минуту на аккаунт 10 000 аккаунтов получают суммарно 600 000 запросов/минуту, то есть 10 000/секунду. Каждый аккаунт соблюдает правило. Если запрос дорогой, сервис всё равно перегружается.

## Ограничения должны переживать смену личности

| Слой | Что ограничивать | Слабое место |
|---|---|---|
| Edge | Соединения, размер тела, грубые всплески | Не знает всех бизнес-операций |
| Учётка/сессия/API key | Число и стоимость операций | Личности и ключи могут ротироваться |
| Организация | Общий бюджет всех её пользователей/ключей | Атакующий может создавать организации |
| Риск-группа | Коррелирующие регистрации и действия | Ошибки классификации, приватность |
| Операция/ресурс | Экспорт, поиск, OTP, получатель сообщения | Можно менять цели атаки |
| Сервис/зависимость | Общая параллельность, очередь, внешние расходы | Нужна справедливость распределения |

Комбинируйте ограничения через **AND**: пройти личный лимит недостаточно, если исчерпан общий. IP — дополнительный сигнал: офисный NAT объединяет людей, а прокси разделяют одного атакующего. Устройство, ASN и fingerprint тоже не являются доказательством личности.

## Приоритетный дизайн для небольшого сайта

1. Каталогизировать дорогие операции: экспорт, график за всю историю, генерация PDF, отправка SMS, создание большого job.
2. Ввести серверные пределы диапазона, числа строк, размера ответа и времени выполнения. Глубина GraphQL — лишь часть оценки; учитывайте fan-out и batch.
3. Ограничить параллельные работы и размер очереди. Не превращать очередь в бесконечное хранилище долгов.
4. Резервировать бюджет до дорогого выполнения. При невозможности резерва вернуть отказ/повтор позже, а не сначала сходить в БД.
5. Сделать квоты на tenant, endpoint и весь сервис. Для новых/непроверенных учёток выделить отдельный небольшой общий пул, чтобы они не вытесняли всех остальных.
6. Для повторяющихся публичных чтений использовать общий кэш или готовые агрегаты. Для приватных данных ключ кэша включает контекст доступа.
7. Изолировать workers тяжёлых задач от интерактивного трафика и админского восстановления.

Нельзя просто поставить глобальный лимит и считать задачу решённой: атакующий способен занять весь разрешённый бюджет. Нужны fairness, резервы для критических путей и адаптация квот к риску.

## Какие проверки действительно полезны

Оценивать возраст учётки вместе с историей поведения, всплески регистраций, концентрацию целей и однотипные последовательности действий. При повышенном риске — задержка выдачи привилегии, дополнительная проверка перед дорогим действием, временное снижение квоты или ручной разбор. Подтверждённый email означает контроль почты, а не уникального человека.

CAPTCHA — дополнительное трение, не гарантия. Если используется challenge-токен, backend проверяет его у провайдера, срок и привязку к действию согласно контракту провайдера. Успех проверки не отменяет лимиты. Для B2B API нужен отдельный путь с ключами и бюджетами, а не обязательный браузерный challenge.

Не собирайте инвазивные сигналы без необходимости. Начинайте с серверной телеметрии, ограничивайте срок хранения; не баньте за один необычный признак. Измеряйте долю ложных блокировок и успешность легитимных сценариев.

## Распределённый лимитер

Лимит в памяти каждого экземпляра обычно умножается с числом экземпляров. Состояние должно учитываться согласованно либо через ограниченные заранее выданные квоты. Операция проверки и списания атомарна; иначе параллельные запросы проходят между check и decrement.

Если счётчик недоступен: публичные дешёвые чтения можно обслужить из кэша в урезанном режиме; дорогое создание заданий разумно временно отказать. Резервные локальные лимиты умножаются при масштабировании, это учитывают отдельно. Сам лимитер тоже имеет конечную ёмкость и не должен создавать неограниченное число ключей от непроверенного ввода.

Не доверяйте X-Forwarded-For от произвольного клиента. Определите доверенные прокси и закройте прямой обход origin. Это отдельная проверка инфраструктуры, не свойство WAF по умолчанию.

## Проверка результата в своей тестовой среде

| Сценарий | Что должно наблюдаться |
|---|---|
| Много аккаунтов, каждый ниже квоты | Общая ёмкость удерживается, критический трафик сохраняет резерв |
| Один запрос с большим batch | Отказ до дорогого выполнения |
| Ротация API keys внутри tenant | Организационный бюджет не сбрасывается |
| Медленная БД | Ограниченная параллельность и очередь, контролируемый отказ |
| Недоступен лимитер | Предсказуемый режим, без неограниченной платной работы |
| Люди за общим NAT | Нет массового постоянного бана по IP |

Метрики: доля успешных полезных действий, p99, очередь и её возраст, стоимость операции, общий расход, регистрации, причины ограничений, challenge completion и обращения по ложным блокировкам. Снижение RPS само по себе не доказывает успех.
