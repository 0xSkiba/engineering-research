# Проблема: боты регистрируют много аккаунтов и держатся под лимитами

> Уверенность: **H** для механизмов, описанных компаниями; **M** для порогов и весов — их нужно подбирать по своим данным.

## Почему лимит «на аккаунт» не работает
Если единственный лимит — `N запросов/мин на аккаунт`, атакующий создаёт K аккаунтов и получает `N×K`. Ротация IP через резидентные прокси обходит и лимит «на IP»: Cloudflare пишет, что ротация IP позволяет обходить IP-репутацию и IP rate limiting ([Cloudflare: residential proxy ML](https://blog.cloudflare.com/residential-proxy-bot-detection-using-machine-learning/)). Stripe про card testing: фильтры по одной эвристике вроде IP «usually not sufficient» ([Stripe docs](https://docs.stripe.com/disputes/prevention/card-testing)).

OWASP классифицирует это как API4 Unrestricted Resource Consumption и API6 Unrestricted Access to Sensitive Business Flows; для API6 рекомендуют device fingerprinting, human detection и выявление нечеловеческих паттернов ([API6](https://owasp.org/API-Security/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/); [API4](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/); [OWASP Automated Threats](https://owasp.org/www-project-automated-threats-to-web-applications/)).

## Цель: сделать атаку дороже выгоды
Полностью остановить ботов нельзя. Цель — чтобы **стоимость одного полезного для атакующего аккаунта/запроса** была выше выгоды. Каждый слой поднимает стоимость: email → телефон → время/возраст → PoW → платёж → ручная проверка.

## Слои (defense in depth)
| # | Слой | Что ловит | Обход | Стоимость для легитимных |
|---|---|---|---|---|
| 1 | Глобальный лимит на эндпоинт (+ load shedding) | Любой шторм, в т.ч. распределённый | Не обходится, но бьёт всех | Деградация при атаке |
| 2 | Лимит по IP, /24 (IPv4) и /48–/64 (IPv6), ASN | Простые скрипты, датацентры | Резидентные прокси | NAT/мобильные сети (CGNAT) |
| 3 | Репутация IP: датацентр/VPN/Tor/прокси | Хостинг-ботов | Резидентные прокси | VPN-пользователи |
| 4 | Fingerprint устройства/TLS (JA3/JA4) | Один скрипт → много аккаунтов | Антидетект-браузеры | Приватность; ложные совпадения |
| 5 | Трение при регистрации: email-верификация, блок одноразовых доменов, телефон, PoW, CAPTCHA/Turnstile | Массовую регистрацию | SMS-фермы, сервисы решения капчи (дорого) | Конверсия |
| 6 | Скорость регистраций (velocity) по IP/подсети/fingerprint/домену email | Волны регистраций | Медленная регистрация | Почти нет |
| 7 | Возраст и репутация аккаунта → доступ к дорогим функциям | «Свежие» армии | Ожидание/прогрев (дороже) | Новые пользователи ждут |
| 8 | Стоимостные лимиты (token bucket с весом запроса) на дорогие эндпоинты, общий бюджет на «кластер» аккаунтов | Распределение нагрузки по аккаунтам | Ещё больше аккаунтов | Почти нет |
| 9 | API-ключи с квотами и тарифами | Анонимное злоупотребление API | Регистрация многих ключей (→ слои 5–7) | Нужна регистрация |
| 10 | Поведенческие аномалии + правила + ручной review | Сложные паттерны | Имитация человека | Ложные срабатывания |
| 11 | Прогрессивные ответы: замедление → челлендж → shadow-ban → бан | Позволяет не банить ложноположительных сразу | — | Минимальная |

## Ключевые идеи
- **Лимиты по нескольким ключам одновременно**: аккаунт, IP, подсеть, ASN, fingerprint, email-домен, телефонный префикс, «кластер» связанных аккаунтов, глобально.
- **Риск-скор вместо бинарных правил**: сумма сигналов → действие (allow / throttle / challenge / deny). Cloudflare Bot Management выдаёт скор 1–99 ([bot score](https://developers.cloudflare.com/bots/concepts/bot-score/)); reCAPTCHA v3 — скор 0.0–1.0 ([reCAPTCHA v3](https://developers.google.com/recaptcha/docs/v3)).
- **Дорогие операции — за возрастом/репутацией**: новые аккаунты получают маленькие квоты.
- **Не сообщать атакующему точную причину отказа** и не отдавать точные пороги; shadow-ban/«тихое» замедление снижает скорость адаптации (**M**).

## Что делать / чего не делать

**Делать**
- Иметь глобальный лимит на каждый дорогой эндпоинт, даже если есть per-user лимиты.
- Ограничивать по нескольким измерениям и считать риск-скор.
- Привязывать квоты к возрасту/репутации аккаунта и верификации.
- Логировать сигналы регистрации (IP, ASN, fingerprint, домен email) для расследований (с учётом GDPR — см. `02-by-product-type/05-crm-customer-databases.md`).

**Не делать**
- Не полагаться только на лимит per-account или только per-IP.
- Не банить по одному сигналу (CGNAT, VPN, корпоративные сети дают ложные срабатывания).
- Не раскрывать пороги и причины блокировки в ответах API.
