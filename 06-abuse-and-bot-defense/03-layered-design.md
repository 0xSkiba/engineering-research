# Конкретный многоуровневый дизайн для небольшого продукта (Remainder-подобный дата-сайт + API)

> Уверенность: архитектура — **M** (собрана из практик Stripe/Cloudflare/Discord/GitHub, см. `02-how-companies-do-it.md`); все числа-пороги — **L**, стартовые значения для настройки по вашим логам. Код: `examples/rate-limit/`.

## Угрозы, под которые проектируем
1. Скрейпинг всех данных через API/HTML (ваш продукт — данные).
2. Массовая регистрация для обхода per-account квот (ваш главный кейс).
3. Credential stuffing на логин.
4. Злоупотребление дорогими эндпоинтами (история, экспорт) → нагрузка на БД и деньги.
5. Злоупотребление бесплатными бонусами/реферальными программами (если появятся).

## Архитектура (снаружи внутрь)
```
Клиент
  │
  ▼
[Edge: Cloudflare]  WAF + rate limiting rules по IP / JA4 / путь; Bot score; Turnstile
  │                 (дёшево, отсекает массовый мусор до вашего сервера)
  ▼
[App: AbuseGate middleware]  token bucket в Redis по ключам:
  │     global(endpoint) · ip · subnet(/24, /48) · asn · fingerprint · account(tier)
  │     + риск-скор (тип IP, UA, возраст аккаунта, верификация, velocity)
  │     → allow / throttle(429) / challenge(Turnstile/PoW) / shadow / deny
  ▼
[Бизнес-логика]  квоты по тарифу/API-ключу, стоимость запроса, кэш тяжёлых ответов
  │
  ▼
[Офлайн]  джобы: кластеризация аккаунтов (общий fp/подсеть/домен/время),
          алерты на всплески регистраций, ручной review, бан кластера целиком
```

## Решения по слоям
| Слой | Реализация | Стартовые значения (L) |
|---|---|---|
| Edge rate limit | Cloudflare rate limiting rule на `/api/*` по IP; отдельное правило для `/api/signup`, `/api/login` | signup: 5/мин на IP; login: 10/мин на IP |
| Регистрация | Turnstile (обязательный Siteverify) + блок одноразовых доменов + канонический email + velocity по подсети/домену | >20 регистраций/час с /24 → ограниченный режим |
| Подтверждение | Email обязателен до доступа к API; телефон — только для повышения квот или при высоком риске | — |
| Квоты по доверию | `accountTier()`: неверифицирован < email < email+телефон+возраст 7 дней < платный | 50 / 200 / 600 / 2000 токенов (ёмкость) |
| Стоимость запроса | `ENDPOINT_COST`: список рынков 1, история 5, экспорт 50 | — |
| Глобальный предохранитель | Ведро на эндпоинт для всех пользователей вместе — защищает БД, когда атака распределена по тысячам аккаунтов | ~70–80% от измеренной ёмкости эндпоинта |
| Fingerprint | Visitor ID (FingerprintJS OSS или edge JA4) + HyperLogLog «аккаунтов на устройство за сутки» | >3 аккаунтов/устройство/сутки → +30 к риску |
| Прогрессивный ответ | `decide()`: 45+ → challenge, 70+ → shadow, 90+ → deny | — |
| API-ключи | Ключ = аккаунт; квоты по тарифу; ключ показывается один раз, хранится хешем; ротация | — |
| Кэш | Публичные «тяжёлые» ответы кэшировать на edge (скрейпинг кэша дешёв для вас) | TTL по свежести данных |
| Офлайн | Ежечасная джоба: группы аккаунтов с общим fp/подсетью/временем регистрации → флаг/бан всего кластера | — |

## Ключевые фрагменты (полный код — в `examples/rate-limit/`)
Многомерная проверка лимитов (все вёдра должны разрешить):
```ts
const buckets: BucketSpec[] = [
  { key: `rl:${ep}:global`,          capacity: 5000, refillPerSec: 500 },
  { key: `rl:${ep}:ip:${sig.ip}`,    capacity: 300,  refillPerSec: 3 },
  { key: `rl:${ep}:net:${sig.subnet}`, capacity: 1500, refillPerSec: 15 },
  ...(sig.fingerprint ? [{ key: `rl:${ep}:fp:${sig.fingerprint}`, capacity: 400, refillPerSec: 4 }] : []),
  ...(actor.accountId ? [{ key: `rl:${ep}:acct:${actor.accountId}`, ...accountTier(actor) }] : []),
];
const lim = await limiter.takeAll(buckets, ENDPOINT_COST[endpoint] ?? 1);
```
Риск-скор и решение:
```ts
const score = riskScore(sig, actor, { subnetSignups1h, fpAccounts24h });
const decision = decide(score, !lim.allowed); // allow | throttle | challenge | shadow | deny
```
Атомарный token bucket — Lua-скрипт в Redis (`token-bucket.lua`), протестирован на fakeredis: 5 запросов проходят при ёмкости 5, шестой получает `retry_after`.

## Почему именно так
- **Глобальное ведро** решает проблему «K аккаунтов × N лимит»: суммарная нагрузка ограничена независимо от числа аккаунтов (как load shedder у Stripe — [Stripe](https://stripe.com/blog/rate-limiters)).
- **Подсеть/ASN/fingerprint** связывают аккаунты одного атакующего, даже если per-account лимиты соблюдены ([OWASP API6](https://owasp.org/API-Security/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/)).
- **Квоты по доверию** делают новые аккаунты дешёвыми для вас и бесполезными для атакующего (аналог usage tiers у [OpenAI](https://platform.openai.com/docs/guides/rate-limits)).
- **Shadow-режим** замедляет обучение атакующего (**M**, общая практика; публичных метрик эффективности не найдено).
- **Turnstile + серверная проверка**: токен одноразовый, 300 с ([Cloudflare](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)).

## Чего мы сознательно НЕ делаем на старте
- Свою ML-модель (нет данных) — сначала правила + логи.
- Обязательный телефон для всех (дорого для конверсии; SMS-фермы всё равно существуют) — только как ступень повышения доверия.
- Блок всех VPN/датацентров (ложные срабатывания; только вес в скоре).

## Метрики и алерты
- Регистрации/час (всего, по подсети, по домену email), доля `restricted`.
- 429/403-челленджи по эндпоинтам; доля прошедших челлендж.
- Нагрузка БД от топ-аккаунтов/кластеров; стоимость запросов на аккаунт.
- Алерт: регистрации > 3× от среднего за неделю для этого часа.

## Приватность и право
Fingerprint, IP, телефон — персональные данные по GDPR. Нужны правовое основание (обычно законный интерес для защиты от мошенничества), срок хранения, упоминание в privacy policy. **Это не юридическая консультация — проверьте с юристом.** См. [GDPR Art. 6](https://gdpr-info.eu/art-6-gdpr/), [Art. 5](https://gdpr-info.eu/art-5-gdpr/).

## Что делать / чего не делать

**Делать**
- Внедрять слои по порядку: edge-лимиты → Turnstile на signup/login → глобальное ведро на дорогих эндпоинтах → квоты по доверию → velocity → fingerprint → офлайн-кластеризация.
- Логировать решения AbuseGate с причиной (внутренне) и смотреть на них еженедельно.
- Банить кластеры, а не отдельные аккаунты.
- Явно выбрать fail-closed/fail-open при недоступности Redis для каждого эндпоинта.

**Не делать**
- Не доверять `X-Forwarded-For` без настроенного `trust proxy`.
- Не возвращать в ответах пороги, счётчики и причину блокировки.
- Не хранить IP/fingerprint бессрочно.
- Не считать капчу достаточной защитой — её решают сервисы за деньги; это лишь один слой.
