# Как организовать написание кода

Ниже **[Рекомендации]**, а не описание единого процесса всех компаний. Основания: [S01, S02, S06, S07](../sources/primary-registry.md).

## Рабочий цикл

| Этап | Конкретный результат | Пример для CRM |
|---|---|---|
| Требования | Сценарий и критерии приёмки | Менеджер экспортирует только клиентов своей организации |
| Проектирование | Границы, модель данных, инварианты | tenant_id обязателен; экспорт не блокирует интерактивный API |
| Анализ угроз | Что может делать недоверенный клиент | Подмена customer_id, повтор задания, огромный диапазон |
| Реализация | Небольшое изменение с понятным владельцем | Сначала API-контракт и ограниченный job, затем UI |
| Проверка | Тест поведения и негативного сценария | Чужой tenant получает отказ, повтор не создаёт второй job |
| Доставка | Воспроизводимый артефакт и план включения | Флаг для тестовой организации; наблюдение ошибок |
| Эксплуатация | Метрики и инструкция действий | Возраст очереди, время экспорта, число отказов, стоимость |

## Начальная архитектура

Для небольшой команды разумная исходная гипотеза: один модульный backend, одна основная реляционная БД, отдельный worker для тяжёлых операций, объектное хранилище файлов. Кэш добавляется под измеренную потребность. Это выбор для проверки, не универсальный стек.

Выделять сервис стоит, если есть самостоятельная граница ответственности и хотя бы одна реальная причина: независимый цикл релизов, особые требования изоляции, существенно иной профиль ресурсов или отдельная команда. Цена — сетевые отказы, версии контрактов, трассировка, согласованность и дополнительные дежурства.

## Тесты по риску

- Unit: расчёт стоимости, переход статуса, округление.
- Integration: настоящая транзакция БД, уникальное ограничение, права между tenant, повторы job.
- Contract: совместимость клиента и API; старый мобильный клиент продолжает работать.
- End-to-end: небольшой набор критических пользовательских путей.
- Load/resilience: установленная ёмкость, медленная зависимость, переполнение очереди, отказ лимитера.

Не оценивайте безопасность числом тестов или процентом покрытия. Уязвимость может находиться в единственном непроверенном условии. Проверяйте ожидаемый отказ, конкурентные запросы и частичный сбой.

## CI/CD для маленькой команды

PR запускает форматирование, типы/линтер, нужные тесты и проверки зависимостей/секретов. Не передавайте production-секреты недоверенному PR. Сборка создаёт идентифицируемый артефакт; один и тот же артефакт проходит среды. Production-права минимальны и отделены от обычного выполнения тестов.

Миграции не прячут внутри случайного старта каждого экземпляра приложения. У них собственный управляемый запуск и контроль блокировок. Релиз не считается успешным по одному health endpoint: проверьте фактический пользовательский путь.

## Когда помогает AI

Просите маленький патч, явные предположения и тесты отказов. Сначала разберите интерфейсы и ограничения проекта. Не позволяйте агенту исправлять падающий тест удалением проверки без разбора причины. Особенно внимательно проверяйте авторизацию, SQL, зависимости, миграции и обработку денег. Сгенерированный код проходит тот же процесс, что написанный человеком.

## Операционные договорённости

Определите SLO для критического пути, срок восстановления RTO и допустимую потерю данных RPO. Их значения зависят от продукта. Для исследовательского сайта устаревший снимок с отметкой времени может быть допустим; для подтверждения оплаты — нет. Запишите, что деградирует первым и кто принимает решение.
